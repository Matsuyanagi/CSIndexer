# CSIndexer CLI 改修依頼（2026-08-11 推敲版）

`docs/SPEC.md`、特に第13章、第16章、第21章、第33章を基準として、以下のCLI機能を改修してください。本書は既存仕様に対する差分要求です。実装時には `docs/CLI.md`、`docs/DECISIONS.md`、`docs/TEST_PLAN.md`、`docs/IMPLEMENTATION_STATUS.md`、`docs/KNOWN_LIMITATIONS.md` も同期してください。

既存の検索結果、profile分離、決定的な並び順、キャンセル、schema v4の旧DB拒否方針、`--short-names` の表示専用変換、`--include-overrides` の子孫方向だけの展開、ラムダ所有関係をcall edgeへ変換しない制約は維持してください。本件ではSQLiteの列追加を必要としないため、原則としてschema versionは変更しません。

## 1. 調査済みの現状と要件の補正

実装前提として、次の現状を考慮してください。

1. `--kind` はすでに `symbol list` と拡張検索時の `symbol find` に存在します。`symbol list` では省略時に `method` と `lambda` の両方を返します。`symbol find` の既存exact検索は型も返せるため、`all` は「常にmethodとlambdaだけ」という新しい種別ではなく、「kindによる追加絞り込みをしない」という意味にします。
2. `IndexedSymbolKind.Method` には通常メソッドだけでなく、コンストラクター、ローカル関数、アクセサー、演算子、変換演算子など、現在methodとして保存される実行可能シンボルが含まれます。この分類は変更しません。
3. 既存の `--async-involved` は「その関数が直接非同期か」ではなく、「非同期起点へ直接または間接的に到達できるか」を `AsyncInvolvementDepth` で絞る機能です。今回追加する直接非同期の条件へ流用しません。
4. 直接非同期かどうかは、すでに保存済みの `AsyncRole` で判定できます。JSONの既存 `isAsync` も `AsyncRole != None` という意味です。
5. 正規化ソースはliteral tokenの `Text` を保存するため、複数行raw string内の改行や、verbatim/raw literal内の実タブが残る場合があります。したがって、単にソース行の前へTABを追加するだけでは「1結果1物理行」も「区切り以外にTABがないこと」も保証できません。single-lineとmulti-lineの両table表示に、保存値を変更しない表示専用サニタイズが必要です。
6. 提示された `string[  ]ValidateReferences` の問題は、宣言シグネチャの型表示ではなく、`SourceNormalizer` が生成してDBへ保存する正規化ソースの問題です。現在のシグネチャ側は `System.String[]` と正しく表示できています。
7. 現在のCLI parserは原則として `--long-option` だけをoptionとして扱い、`-o` は位置引数として解釈されます。また、通常出力とgraph出力は `Console.WriteLine` を直接使用しています。ファイル出力には短縮optionの解析と、出力先 `TextWriter` の共通化が必要です。
8. `index` と `conditions` はmethod/lambdaを検索対象にするコマンドではありません。ここで `--kind` や直接非同期条件を受理しても無意味なno-opになるため、「全コマンド」は「method/lambdaを候補またはrootとして扱う全検索コマンド」と読み替えます。`index` と `conditions` は対象外とし、誤指定時は従来どおり未知optionとして拒否してください。
9. 現在の出力形式option名は `--output` ですが、本改修では後方互換性を維持せず `--output-format` へ変更します。旧option名をaliasやdeprecated optionとして残しません。

## 2. 共通の関数種別条件

### 2.1 CLI構文

method/lambdaを扱う検索コマンドで、次のoptionを共通利用できるようにしてください。

```text
--kind all|method|lambda
```

既定値は `all` です。明示的な `--kind all` と `--kind` 省略時は、候補、結果順、終了コード、table/JSON内容が同一でなければなりません。

値の意味は次のとおりです。

- `all`: kind述語を追加しない。DBへ `All` というkindを保存せず、既存の「kind指定なし」と同じ内部表現にする。
- `method`: `IndexedSymbolKind.Method` だけを対象にする。
- `lambda`: `IndexedSymbolKind.Lambda` だけを対象にする。

未知値のエラーは、少なくとも有効値をすべて示してください。

```text
Unknown symbol kind: <value>. Use all, method, or lambda.
```

### 2.2 適用対象と適用位置

`--kind` は、各コマンドで次の対象へ適用してください。二次的に表示されるcaller、callee、graph nodeまで一律に削除して、既存の検索意味やgraph到達性を壊してはいけません。

| コマンド | `--kind` を適用する対象 | 補足 |
|---|---|---|
| `symbol find` | 一致symbol | `all` は既存exact型検索も妨げない |
| `symbol list` | 一覧symbol | `all` ではmethodとlambdaを返す既存挙動 |
| `source show` | ソース表示対象symbol | source-backed executableだけという既存制約を維持 |
| `source search` | ソース検索結果symbol | source条件とANDで結合 |
| `definition <query>` | 解決対象およびdefinition結果 | lambdaの定義表示を可能にする |
| `definition --at` | 位置から解決したdefinition結果 | filter不一致なら0件 |
| `references` | 検索対象となる参照先symbol | 返されるcallerのkindを絞るoptionではない |
| `callers` | 検索対象となるcallee symbol | `--caller-scope` の結果kindを絞るoptionではない |
| `callees` | 呼び出し元となるroot symbol | 返されるcalleeのkindを絞るoptionではない |
| `async tree` | 一意に解決するroot | 保存済みpathの途中nodeは絞らない |
| `callers tree` | 一意に解決するroot | graph内のcaller nodeは絞らない |
| `overrides` | methodであるrootとoverride関係 | lambdaへoverrideを擬似適用しない |

`index` と `conditions` は `--kind` を受理しません。

### 2.3 ラムダqueryの解決

現在、ラムダの検索規則は主に `symbol find` の拡張検索にだけ実装され、legacy exact resolverとgraph root resolverはmethod queryを前提にしています。`--kind` を共通化するため、method/lambda用の共通target resolverを用意し、少なくとも既存仕様にある次のラムダ表記を各該当コマンドで一貫して解決してください。

```text
::<lambda#1>
Owner()::<lambda#2>
Namespace.Type::Owner()::<lambda#2>
::<lambda#*>
```

複数targetを扱えるコマンドは、既存の安定順ですべて処理します。一意rootが必要な `async tree` と `callers tree` は、既存のgraph ambiguity契約に従って候補を列挙してエラーにしてください。エラー文の `method` 固定表現は、lambdaも含む `source-backed executable` へ更新してください。

ただし、lambdaへのdelegate `Invoke()`、event、callback、reflection、runtime flowは現在インデックス化していません。`references` や `callers` に `--kind lambda` を指定しても、保存済みの実call/reference edgeがない関係を推測で生成してはいけません。この制約は `docs/KNOWN_LIMITATIONS.md` に明記してください。

### 2.4 method専用機能との組み合わせ

- `--include-overrides` は引き続きmethod専用です。
- exact method queryでは `--kind all` または `--kind method` と `--include-overrides` を併用可能にしてください。現在の「kind optionが存在するだけで一律拒否」という判定は見直してください。
- `--kind lambda` と `--include-overrides` は引数エラーにしてください。
- `overrides --kind all` はmethodにだけ既存処理を適用します。
- `overrides --kind lambda` は空結果のno-opにせず、`--kind lambda is not applicable to overrides.` のように理由を示す引数エラーにしてください。
- method専用の展開や表示規則をlambdaへ擬似適用してはいけません。同様に、lambda専用の所有・採番規則をmethodへ適用してはいけません。

## 3. 直接非同期かどうかの共通検索条件

### 3.1 CLI構文

`--kind` と同じ検索コマンド群へ、次のoptionを追加してください。

```text
--async-status all|async|sync
```

既定値は `all` です。明示的な `--async-status all` とoption省略時は同一結果でなければなりません。

値の意味は次のとおりです。

- `all`: 直接非同期かどうかで絞らない。
- `async`: `AsyncRole != AsyncRole.None` のmethod/lambdaだけを対象にする。
- `sync`: `AsyncRole == AsyncRole.None` のmethod/lambdaだけを対象にする。

型などの非関数symbolを `AsyncRole.None` という理由だけで `sync` に含めてはいけません。`async` と `sync` はmethod/lambda候補にだけ適用してください。

未知値のエラーは次のように有効値を示してください。

```text
Unknown async status: <value>. Use all, async, or sync.
```

`index` と `conditions` はfunction targetを持たないため、`--async-status` も受理しません。

### 3.2 非同期判定

query時に名前やソース文字列から再判定せず、インデックスへ保存済みの `AsyncRole` を使用してください。`async` には、現在の仕様で次のいずれかのdirect roleを持つ関数を含めます。

- `DeclaredAsync`
- `ReturnsAwaitable`
- `ContainsAwait`
- `AsyncIterator`
- `ReturnsAsyncEnumerable`
- `AsyncVoid`
- `UniTaskVoid`
- `UsesAwaitForEach`
- `UsesAwaitUsing`

これにより、`async` keywordがなくても既知の `Task` / `Task<T>`、`ValueTask` / `ValueTask<T>`、`UniTask` / `UniTask<T>` を返す関数は `async` に含まれます。逆に、名前が `Async` で終わるだけの同期関数は含めません。custom awaitableは、既存の `AsyncRole` 抽出で認識できる範囲を超えて名前から推測しません。

### 3.3 `--async-involved` との区別と合成

既存の `symbol list --async-involved` は削除、改名、意味変更しません。

- `--async-status` は直接的な性質である `AsyncRole` を見る。
- `--async-involved` は派生情報である `AsyncInvolvementDepth != null` を見る。
- 両方を指定した場合はAND条件にする。

特に、`AsyncRole == None` でも非同期関数を呼ぶため `AsyncInvolvementDepth > 0` の関数は、`--async-status sync --async-involved` に一致します。この区別を直接テストしてください。

### 3.4 他の検索条件との順序

kind、async status、profile、generated filter、名前、source include/exclude、override展開は、最終的にAND条件として一貫した結果を返してください。`--include-overrides` を使う場合は実在するmethod候補を展開した後、各targetへkind/async statusを適用し、その絞り込み済みtarget集合を `definition`、`references`、`callers`、`callees` の処理へ渡してください。

graphコマンドではkind/async statusをrootの解決だけに使い、保存済みasync pathやcaller graphの途中nodeをfilterして経路を切断してはいけません。

## 4. ソースを1結果1行で表示するtable layout

### 4.1 CLI構文と既定値

正規化ソースをtable表示するコマンドへ、次のoptionを追加してください。

```text
--source-layout single-line|multi-line
```

- 既定値は `single-line` とする。
- `multi-line` を指定した場合は、現在のsymbol行と、それに続く `    source: <normalized-source>` 行というhuman-readableな表示を維持する。
- `symbol find` では `--show-source` 指定時だけ有効とする。
- `source show` と `source search` は常にソースを表示するため、そのまま利用できる。
- `--output-format json` では既存の構造化JSONを変更しない。`--source-layout` とJSONの併用、またはソースを表示しないコマンドでの指定は、無視せず引数エラーにする。

未知値では次のように有効値を示してください。

```text
Unknown source layout: <value>. Use single-line or multi-line.
```

### 4.2 `single-line` のコマンド別固定record形式

単一行table layoutのfield数とfield順は、全コマンドで同じにする必要はありません。コマンドとoptionの組み合わせごとにrecord schemaを定義し、同じ1回の実行中では、すべての結果recordが同じfield数とfield順を持つようにしてください。

少なくともsymbol/source系コマンドは次の形式にします。

| コマンド形式 | 1recordの形式 | field数 | 区切りTAB数 |
|---|---|---:|---:|
| `symbol find` | `<signature><TAB><path>:<line>:<column>` | 2 | 1 |
| `symbol find --show-source` | `<signature><TAB><path>:<line>:<column><TAB><normalized-source>` | 3 | 2 |
| `source show` | `<signature><TAB><path>:<line>:<column><TAB><normalized-source>` | 3 | 2 |
| `source search` | `<signature><TAB><path>:<line>:<column><TAB><normalized-source>` | 3 | 2 |
| `symbol list` | `<signature>` | 1 | 0 |

例:

```text
private static System.String[] CsIndex.Core.Input.WorkspaceLoader::ValidateReferences(System.Collections.Generic.IEnumerable<System.String>)<TAB>E:\WorksDevelop\CSIndexer\src\CsIndex.Core\Input\WorkspaceLoader.cs:230:5<TAB>private static string[]ValidateReferences(IEnumerable<string>references){...}
```

fieldの契約は次のとおりです。

- field separatorにはTAB `U+0009` を使用する。見た目上の複数spaceで代用しない。
- `<signature>` は既存の宣言形式signatureと、該当する場合のasync注釈を含む1fieldとする。async情報の有無によってfield数を変えない。
- `--short-names` は従来どおり `<signature>` の表示名へ適用する。
- locationは既存情報を失わないよう、例示された `path:line` ではなく現在の `path:line:column` を使用する。
- `symbol list` はsignatureだけを1recordとして出力し、各recordへTABを追加しない。
- 1回のコマンド実行中に、sourceの有無やmetadata/source-backedの違いによってfield数を変えない。
- source-backedだけを返す `source show` / `source search` では、3fieldすべてが非空になる。
- `symbol find` はmetadata-only候補も返し得る。source locationがない候補ではlocationを空文字にし、TABを1個出して2fieldを維持する。
- `symbol find --show-source` は表示optionであり候補をsource-backedへ限定しない既存仕様を維持する。metadata-only候補ではlocationとnormalized-sourceを空文字にし、それでもTABを2個出して3fieldを維持する。表示のために候補を削除してはいけない。
- 上表以外のsingle-line table出力を変更する場合も、コマンドごとのfield schemaを `docs/CLI.md` に明記し、同じ実行中に可変長recordを混在させない。

コマンド形式ごとに、例えば次の1種類の正規表現で全結果recordを分解できるようにしてください。

```regex
# symbol find
^(?<signature>[^\t]+)\t(?<location>[^\t]*)$

# symbol find --show-source / source show / source search
^(?<signature>[^\t]+)\t(?<location>[^\t]*)\t(?<source>[^\t]*)$

# symbol list
^(?<signature>[^\t]+)$
```

### 4.3 record以外のstdoutを混在させない

`single-line` layoutのstdoutにはrecord行だけを出してください。現在の `Query matched N symbol(s):`、`N symbol(s):`、空行、indent、`source:` prefixをstdoutへ混在させません。

件数summaryは利便性のため削除せず、`single-line` ではstderrへ出力してください。0件の場合はstdoutを空にし、`Query matched 0 symbol(s):` または `0 symbol(s):` をstderrへ出します。warning、progress、errorも従来どおりstderrです。`-o` / `--output-file` を指定した場合も、recordだけをファイルへ書き、件数summaryはstderrへ出してください。

`multi-line` layoutでは後方互換用として現在のheading、indent、symbol行、`    source:` 行を維持します。ただし、signature行とsource行のそれぞれを必ず1物理行にしてください。raw stringやliteral内の改行によって、1つの `source:` 表示が複数の物理行へ分裂してはいけません。

このrecord-only契約は上表のsymbol/source系single-line table出力に適用します。`callers` の補助section、tree、Mermaidなど、異なる構造を持つ全table出力を本件でTSVへ再設計しません。それらを機械処理する場合は既存JSONを使用します。

### 4.4 TABと改行の表示サニタイズ

`single-line` の各field、および `multi-line` のsignatureとnormalized-sourceを出力する直前に、次の文字をASCII space `U+0020` へ置換してください。

- TAB `U+0009`
- CRLF（1個のspaceへ置換）
- 単独のCR `U+000D`
- 単独のLF `U+000A`
- 1物理行を分断し得る `U+0085`、`U+2028`、`U+2029`

`single-line` では、各recordに存在するTAB `U+0009` が、そのコマンド形式で定義したfield separatorだけになるようにしてください。特に `<normalized-source>` 内にはTABを残しません。

`multi-line` ではsignatureとnormalized-sourceを別の表示行にしますが、normalized-source内の実TABやraw string内の改行も同じ規則でspaceへ置換し、`    source: <normalized-source>` 全体を1物理行にしてください。ソースに書かれた2文字のescape sequence `\t` や `\n` は実制御文字ではないため、そのまま残します。

この変換はtableの表示層だけで行います。DB内の `normalized_source`、`normalized_source_hash`、source検索、JSONの `normalizedSource` は変更しません。JSONでは制御文字がJSON escapeされる既存のlosslessな値を維持してください。

## 5. 配列rankの不要な空白を正規化ソースから除去する

現在、Roslynのarray rankに含まれるsource幅0のomitted tokenがseparator判定へ入り、正規化ソースが次のようになります。

```text
private static string[  ]ValidateReferences(...)
```

source文字を持たないmissing/omitted tokenを正規化文字列へ追加したり、その前後のseparator判定へ使ったりしないよう `SourceNormalizer` を修正してください。ただし、literal tokenや実際のsource文字を持つtokenを削除してはいけません。

少なくとも次を満たしてください。

```text
string[]args
int[,]matrix
int[][]values
string?[]items
```

正規化規則は「連結して別tokenへ変化する場合だけ1個のspaceを入れる」という既存方針を維持します。そのため `]` と識別子の間にseparatorが不要なら、要求例どおり `string[]args` として構いません。通常の宣言表示signatureに必要な可読用spaceは `SymbolSignatureFormatter` 側で維持してください。

修正後の文字列から `normalized_source_hash` を再計算してください。schema形状は変わらないためschema versionは上げませんが、入力が同じでも古い正規化結果をcache reuseしないよう、`RequestHasher.ToolVersion` または同等の解析cache versionを更新してください。既存DBには古い正規化ソースが残るため、次回indexで確実に再解析されること、および既存DBを直接queryする場合は `index --rebuild` が必要であることを文書化してください。

## 6. 結果をファイルへ出力するoption

### 6.1 CLI構文

stdoutへ結果を出すコマンドへ、次の同義optionを追加してください。

```text
-o <path>
--output-file <path>
```

出力形式optionは、既存の `--output` から次の名前へ変更してください。

```text
--output-format <format>
```

commandごとの有効値は現在と同じです。

- 通常のsymbol/source/query/conditions出力: `table|json`
- `async tree`: `tree|line|json`
- `callers tree`: `tree|mermaid|json`

`-o` は `--output-format` の短縮形ではありません。`--output-format` は出力形式、`-o` / `--output-file` は出力先です。ファイル拡張子から形式を推測しません。

後方互換性は不要です。旧 `--output` はaliasとして残さず、指定された場合は未知optionとして終了コード `2` で拒否してください。deprecation warningを出して受理する挙動も実装しません。global help、各command help、usage、エラー文、テスト、正式文書の表記をすべて `--output-format` へ置き換えてください。

対象は次のとおりです。

- `symbol find`
- `symbol list`
- `source show`
- `source search`
- `definition`
- `references`
- `callers`
- `callees`
- `overrides`
- `async tree`
- `callers tree`
- `conditions`

`index` の現在の進捗とsummaryはstderr出力であり、検索結果stdoutを持たないため対象外です。helpも通常どおりstdoutへ表示し、結果ファイルへredirectしません。

### 6.2 出力契約

- option省略時は現在と同じくstdoutへ出力する。
- option指定時は、stdoutへ出るはずだった結果payloadをファイルへ出力し、成功時のstdoutは空にする。
- warning、progress、argument/query/database/output errorはstderrのままにする。
- relative pathはprocessのcurrent directoryを基準に絶対化する。
- 短縮optionとして特別扱いするのは完全一致する `-o` だけとし、`-opath` や `-o=<path>` を暗黙に受理しない。
- UTF-8 without BOMで出力する。
- 既存ファイルは成功時に置き換える。
- 正規化した出力先pathが使用中のSQLite DB pathと一致する場合は、DB破壊を防ぐため引数エラーにする。
- parent directoryが存在しない場合は暗黙作成せず、明示的なoutput errorにする。
- argument error、query error、database error、cancel、書き込み失敗時に、既存の出力先をtruncateしたり、部分的な最終ファイルを残したりしない。同一directoryの一時ファイルへ書き、成功時だけ置換するなどの方法で保証する。
- `-o` と `--output-file` の併用、または同じoptionの複数指定は「1回だけ指定可能」という引数エラーにする。
- `-o` の値がない場合や空の場合は既存option parserと同じ引数エラー規則に従う。
- output I/O errorは `Output error:` で始め、既存の終了コード体系ではanalysis failureの `3` を使用する。

### 6.3 実装上の境界

`Console.SetOut` によるprocess-globalな切り替えへ依存せず、`OutputFormatter`、`GraphOutputFormatter`、JSON writer、conditions writerへ共通の `TextWriter` を注入してください。これにより、テストの並列性を壊さず、stdoutとfileで同じformatterを使用し、形式差分を防いでください。writerの所有権とdispose責務を明確にし、stdout writerを誤ってcloseしないでください。

## 7. エラーと後方互換性

- 未知option、未知値、重複optionは部分結果を出さず、既存どおり終了コード `2` にする。
- query結果0件は、既存コマンドがエラーと定めていない限り成功とする。一意rootが必要なgraphコマンドは既存の0件・曖昧エラー契約を維持する。
- `--require-single` はkind/async statusを適用した後の件数で判定する。
- `--short-names`、`--exclude-generated`、`--only-generated`、`--dispatch`、`--caller-scope`、`--exclude-lambda-calls` の意味は変更しない。
- JSON property名、root shape、canonical fieldは変更せず、filterによって配列要素だけを絞る。
- 出力形式option名はbreaking changeとして `--output-format` へ置き換え、旧 `--output` を受理しない。
- tableの表示サニタイズは保存値へ反映せず、DB、source検索、JSONでは保存済み正規化ソースのliteral内容を変更しない。
- delegate/event/callbackの実行位置推論、runtime dispatchの完全展開、Source Link、外部decompile、schema migrationは本件の対象外とする。

## 8. 必須テスト

実装前にfocused testを追加し、期待した理由で失敗することを確認してから実装してください。少なくとも次を自動テストで直接検証してください。

### 8.1 `--kind`

1. `symbol list` と `symbol find` で、option省略と `--kind all` のID集合、順序、table/JSON出力が一致する。
2. `--kind method` がlambdaを除外し、`--kind lambda` がmethodを除外する。
3. 通常メソッド、コンストラクター、ローカル関数、アクセサー、演算子、変換演算子が `method` に含まれる。
4. 適用対象matrixにある各コマンドが `all|method|lambda` を正しくparseし、filterを指定されたtarget位置へ適用する。
5. lambdaを `definition`、`callees`、`async tree`、`callers tree` のtarget/rootとして解決できる。複数一致するgraph rootは安定順の候補付きで失敗する。
6. `overrides --kind all` は既存method結果を維持し、`overrides --kind lambda` は明示的な非適用エラーになる。
7. exact method queryの `--include-overrides --kind all` と `--include-overrides --kind method` が動作し、`--kind lambda` との併用を拒否する。
8. `index` と `conditions` は `--kind` を未知optionとして拒否する。

### 8.2 `--async-status`

1. option省略と `--async-status all` の結果が一致する。
2. `async Task`、async keywordなしの `Task<T>`、`ValueTask`、`UniTask<T>`、`UniTaskVoid`、async stream、async lambdaが `async` に含まれる。
3. `Async` suffixだけを持つ通常の同期関数が `sync` に含まれ、`async` には含まれない。
4. nested lambda/local functionのroleが外側関数へ漏れず、それぞれ正しいstatusで絞られる。
5. `AsyncRole.None` かつ `AsyncInvolvementDepth > 0` の関数が `--async-status sync --async-involved` に一致する。
6. 型symbolが `sync` に混入しない。
7. `--include-overrides` 後の実target集合にstatus filterが適用される。
8. graphではrootだけを絞り、途中nodeを削除せず既存path/edgeを維持する。
9. `index` と `conditions` は `--async-status` を未知optionとして拒否する。

### 8.3 ソースlayout

1. `symbol find` は2field/1TAB、`symbol find --show-source`、`source show`、`source search` は3field/2TAB、`symbol list` は1field/0TABになる。
2. 同じ1回の実行に含まれる全結果recordが同じfield数とfield順を持ち、それぞれ1種類の正規表現で分解できる。
3. default single-lineのstdoutにheading、indent、`source:` 行が混在しない。件数summaryはstderrへ出力し、0件ではstdoutだけが空になる。
4. `-o` / `--output-file` 指定時も、recordだけをファイルへ書き、件数summaryはstderrへ出力する。
5. `--source-layout multi-line` が既存のheading、symbol行、`    source:` 行を維持し、signature行とsource行をそれぞれ1物理行にする。
6. source内の実TAB、CRLF、CR、LF、Unicode line separatorをsingle-lineとmulti-lineのtable表示でspaceへ変換する。
7. literal内の実TABとraw string内改行が、single-line recordもmulti-lineの `source:` 行も分断しない。
8. DBの `normalized_source` とhash、source検索、JSONの `normalizedSource` は表示サニタイズ前の値を維持する。
9. metadata-only symbolを含む `symbol find` と `symbol find --show-source` でもfield数が変わらず、location/sourceなしを空fieldで表現する。
10. `--source-layout` とJSON、またはソース非表示コマンドとの不正な組み合わせを拒否する。

### 8.4 配列正規化

1. `string[] args`、多次元配列、jagged array、nullable element/arrayを正規化して、rank内に不要なspaceが入らない。
2. array creationの実サイズ式、attribute bracket、indexer、collection expressionなど、別用途のbracketを壊さない。
3. comment除去、token境界、interpolated/raw literal保存の既存testがすべて通る。
4. 修正後のtextからSHA-256 hashが再計算される。
5. 同じ入力でも旧cacheが再利用されず、再index後のDBに修正済みソースが保存される。

### 8.5 ファイル出力

1. `-o` と `--output-file` が同じ結果を生成する。
2. table、JSON、async tree/line/JSON、caller tree/Mermaid/JSON、conditionsの各writerで、ファイル内容が通常stdout内容と一致する。
3. 成功時のstdoutが空で、stderrのwarning/progressはredirectされない。
4. UTF-8 BOMが付かない。
5. 既存ファイルを成功時に置換できる。
6. query/format/write/cancel失敗時に既存ファイルを変更せず、一時ファイルを残さない。
7. missing value、空path、重複指定、存在しないparent directoryを明示的に失敗させる。
8. `--output-format` と `-o` を同時利用でき、拡張子ではなく `--output-format` が形式を決める。
9. 出力先と使用中DBが同一pathの場合は、DBを変更せずに拒否する。
10. 現在 `--output` を受理している全commandで `--output-format` が同じformat値と既定値を引き継ぎ、旧 `--output` は未知optionとして拒否される。
